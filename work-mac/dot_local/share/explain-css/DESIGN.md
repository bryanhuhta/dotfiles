# explain.css: design guide

## Purpose

`explain.css` is a single, self-contained stylesheet for agent-generated technical documents. It is not specific to any one document genre. A pull request or code review summary, an architecture walkthrough, a system analysis, and an incident postmortem all use the same page shell, the same admonitions, the same diagrams, and the same tables; only the section headings and the prose change from one genre to the next. The stylesheet is designed for reading on a laptop, at length, in the manner of a well-typeset paper rather than a marketing page or a dashboard. Documents built with this stylesheet use plain, precise, declarative technical prose in the tradition of an IETF RFC. This prose register is not conversational, and it is not marketing-toned.

The stylesheet is paper-toned only. The background is a warm, slightly off-white paper color. The ink color is a soft near-black. There is exactly one palette. The stylesheet defines no dark mode, no `prefers-color-scheme` branching, and no `[data-theme]` switching of any kind. Do not add any of these.

The file is fully self-contained. It uses only system font stacks. It never uses `@import` and never links to an external font, icon set, or script. Every visual effect, including all diagram primitives, is produced in plain CSS against semantic HTML. No JavaScript is required or expected anywhere. An agent building a document against this stylesheet needs nothing beyond this file, the HTML it writes, and this guide.

## Do

- Do use an admonition (`.admonition.note/tip/warning/important/danger`) only for content the reader could skip without losing the main thread: a caveat, a recommendation, a risk, or a blocking concern. If a sentence is part of the normal explanatory flow of the document, it belongs in a plain paragraph, not in a callout.
- Do use `.ref-*` classes to bind one entity (a function, service, module, branch, or file) to one color across the whole document. Color the entity's name in prose with `<code class="ref-red">` or `<span class="ref-red">`. Use the exact same class on that entity's box, segment, or node wherever it appears in a diagram.
- Do accompany any diagram that uses `.ref-*` fills with a `.legend` listing each color's meaning. A ref color with no nearby legend is a bug in the document, not a stylistic choice.
- Do keep the palette of `.ref-*` colors small in any one document. As a rule of thumb, 2 to 4 distinct entities per document is legible. 5 to 6 (the full set) is the hard ceiling. Beyond that ceiling, readers cannot hold the color mapping in their head. If a document has more entities than the ceiling allows, group the entities or fall back to plain labels for the less important ones instead of inventing new hues.
- Do keep admonition colors and `.ref-*` colors visually separate. Admonition hues (blue for note, green for tip, orange for warning, purple for important, red for danger) are reserved for admonitions only. An admonition hue must never be reused as an entity color. Conversely, a `.ref-*` color must never be applied to a bordered, left-accented, labeled block. A `.ref-*` color appears only as bare tinted inline text or as a diagram fill. If a reader has to ask whether a box is red because it signals danger or because it represents the `eventHandler` entity, the document has broken this rule.
- Do use inline `<code>` (no class needed) for short literal tokens referenced in prose: variable names, function names, file paths, flags, and single values such as `true` or `42`.
- Do use `<pre class="code-block"><code>...</code></pre>` for any snippet that stands on its own: content spanning more than one line, an actual diff, or code the reader is meant to read from top to bottom rather than as a token within a sentence.
- Do use `.line-focus` sparingly, on at most one or two lines per code block, to mark a line of interest in ordinary (non-diff) code. Do not combine `.line-focus` with `.line-add` or `.line-remove` on the same line.
- Do use `.diff-split` as the default presentation for a diff between two versions of the same file or function. Reserve a single unified `pre.code-block` (with `.line-add` and `.line-remove` mixed in one column) for a narrow embed, a small inline snippet, or a change too short to benefit from two columns.

## Do not

- Do not invent new admonition types or new `.ref-*` hues. The five admonition variants and the six ref colors are complete, closed sets. Pick the closest existing one instead of adding inline styles or new classes.
- Do not use an admonition as a generic highlighted box for emphasis. If none of the note, tip, warning, important, or danger semantics apply, use a blockquote, a `.compare-col`, or a plain paragraph instead.
- Do not type `+`, `-`, or `→` characters at the start of a diff or focus line. The gutter marks in `.line-add`, `.line-remove`, and `.line-focus` are generated by CSS. Typing these characters manually doubles the marks.
- Do not put a `.ref-*` class on an `.admonition`. Do not nest an admonition inside a diagram primitive to color it. These two systems never overlap on the same element.
- Do not reuse the same `.ref-*` color for two different entities in one document, even after the palette is exhausted. Reuse breaks the one-color-one-entity guarantee the mechanism depends on. Group entities or drop the coloring for minor entities instead.
- Do not add dark-mode support, a theme toggle, or any `prefers-color-scheme` or `[data-theme]` rule to this stylesheet under any circumstance.
- Do not use em dashes or en dashes anywhere in generated document prose, and do not substitute a double hyphen for one. This is a standing rule for any document produced with this stylesheet, not a one-time cleanup. Future authors must restructure the sentence instead: use a comma, a colon, a semicolon, parentheses, or split the sentence into two.
- Do not let the two panes of a `.diff-split` fall out of row alignment. When a line exists on only one side (a pure addition or a pure deletion), insert a matching `.line-empty` placeholder line at the same row on the other side. A `.diff-split` where line 6 on the left does not correspond to line 6 on the right is a bug in the document.

## Component catalog

### Page shell

Wrap the whole document in `<div class="doc">`. This element sets the measure, centers the page, and provides the outer margins. Everything else lives inside it. The measure is fluid, not fixed: it scales with the viewport up to a cap of approximately 1180px, so the document fills most of the available window width instead of sitting in a narrow fixed column. The cap exists only to keep prose readable on very wide monitors; do not remove it and do not lower it to the old 760px value.

```html
<div class="doc">
  <!-- header, toc, sections, footer -->
</div>
```

### Header block

`.doc-header` groups a `.kicker` (a small uppercase eyebrow line), an `<h1>` title, an optional `.dek` (an italic subtitle or summary line), and a `.byline` (a small meta line, with `<span class="sep">·</span>` between fields). The kicker and the byline are freeform text, not a fixed vocabulary; set each to whatever names the document's genre and source. A diff explanation, a postmortem, and a system analysis each use different kicker and byline text on the same markup.

```html
<header class="doc-header">
  <p class="kicker">Diff Explanation</p>
  <h1>Refactor the retry queue</h1>
  <p class="dek">How <code>retryWorker</code> moved from polling to event-driven dispatch.</p>
  <p class="byline">Generated from diff <code>a1b2c3d</code> vs <code>main</code><span class="sep">·</span>2026-08-13</p>
</header>
```

```html
<header class="doc-header">
  <p class="kicker">Incident Postmortem</p>
  <h1>Checkout latency spike on 2026-07-30</h1>
  <p class="dek">A stale connection pool held the payments service at 40% capacity for eleven minutes.</p>
  <p class="byline">INC-4821<span class="sep">·</span>Severity: high<span class="sep">·</span>Resolved 2026-07-30</p>
</header>
```

```html
<header class="doc-header">
  <p class="kicker">System Analysis</p>
  <h1>How the notification pipeline routes an alert</h1>
  <p class="dek">A walkthrough of the path from a firing rule to a delivered webhook.</p>
  <p class="byline">Covers <code>pkg/services/ngalert</code><span class="sep">·</span>2026-08-13</p>
</header>
```

### Table of contents

`.toc` wraps a `.toc-title` label and a nested `<ol>` or `<ul>` of links. Nest another `<ol>` or `<ul>` inside an `<li>` for subsections.

```html
<nav class="toc">
  <p class="toc-title">Contents</p>
  <ol>
    <li><a href="#background">Background</a></li>
    <li><a href="#changes">Changes</a>
      <ol>
        <li><a href="#retry-queue">Retry queue</a></li>
        <li><a href="#worker">Worker dispatch</a></li>
      </ol>
    </li>
  </ol>
</nav>
```

### Admonitions

`<div class="admonition VARIANT">`, where VARIANT is one of `note`, `tip`, `warning`, `important`, or `danger`. The uppercase label is generated by CSS from the class. Do not add your own "Note:" text. Content consists of plain paragraphs.

```html
<div class="admonition warning">
  <p>This change silently drops retries older than 30 seconds; confirm no caller depends on unbounded retry.</p>
</div>
```

### Inline code

Plain `<code>myToken</code>` requires no class. It automatically receives the mono font, background chip, and border.

```html
<p>The fix renames <code>flushQueue</code> to <code>drainQueue</code>.</p>
```

### Code / diff blocks

`<pre class="code-block"><code>` wraps one `<span class="line">` per line of source. Add `line-add` for an added line, `line-remove` for a removed line, or `line-focus` to mark a line of interest without diff semantics. Gutter marks (`+`, `−`, `→`) are generated by CSS. Never type them yourself. An optional `.code-block-title` directly before the `<pre>` adds a filename caption.

```html
<div class="code-block-title">src/queue/retryWorker.js</div>
<pre class="code-block"><code><span class="line line-remove">setInterval(poll, 1000);</span>
<span class="line line-add">queue.on('enqueued', dispatch);</span>
<span class="line line-focus">dispatch(); // now event-driven, not polled</span>
<span class="line">module.exports = { dispatch };</span></code></pre>
```

### Side-by-side diff

`.diff-split` holds two `.diff-pane` columns: `.diff-pane-head` on the left for the base version, `.diff-pane-new` on the right for the changed version. Each pane contains its own `.diff-pane-label` (the text "HEAD" or "NEW", set by the author, not generated by CSS) followed by a normal `pre.code-block`, using the same `.line`, `.line-add`, `.line-remove`, and `.line-focus` classes documented above. When a line has no counterpart on the other side, fill that row with `<span class="line line-empty">` so the two panes stay aligned line for line.

```html
<div class="diff-split">
  <div class="diff-pane diff-pane-head">
    <p class="diff-pane-label">HEAD</p>
    <pre class="code-block"><code><span class="line">function drain(queue) {</span>
<span class="line line-remove">  setInterval(() => poll(queue), 1000);</span>
<span class="line line-empty"></span>
<span class="line">}</span></code></pre>
  </div>
  <div class="diff-pane diff-pane-new">
    <p class="diff-pane-label">NEW</p>
    <pre class="code-block"><code><span class="line">function drain(queue) {</span>
<span class="line line-add">  queue.on('enqueued', () => dispatch(queue));</span>
<span class="line line-add">  queue.on('drained', () => log('idle'));</span>
<span class="line">}</span></code></pre>
  </div>
</div>
```

### Stat pills

`.stat-group` wraps one or more `.stat-pill` badges. Use the `.stat-pill-add` and `.stat-pill-remove` modifiers for green and red diff-summary counts.

```html
<div class="stat-group">
  <span class="stat-pill stat-pill-add">+42</span>
  <span class="stat-pill stat-pill-remove">−11</span>
  <span class="stat-pill">7 files changed</span>
</div>
```

### Legend (required alongside any `.ref-*` diagram)

`.legend` wraps one `.legend-item` per entity. Each `.legend-item` contains a `.legend-swatch` (colored with the matching `.ref-*` class) and a label.

```html
<div class="legend">
  <span class="legend-item"><span class="legend-swatch ref-blue"></span> retryWorker</span>
  <span class="legend-item"><span class="legend-swatch ref-amber"></span> queueStore</span>
</div>
```

### Entity/ref colors

There are six ref classes: `.ref-red`, `.ref-blue`, `.ref-green`, `.ref-amber`, `.ref-teal`, and `.ref-purple`. Each class applies identically to inline prose (`<code>` or `<span>`) and to diagram fills (`.tree-node`, `.flow-step`, `.bar-segment`, `.legend-swatch`, `.block-grid-cell`). The same class produces the same hue family in both contexts, so a reader can match a word in a sentence to a box in a diagram. See the Do and Do not sections above for the rule that keeps ref colors distinct from admonition colors.

```html
<p>Once <code class="ref-blue">retryWorker</code> reads from <code class="ref-amber">queueStore</code>, it dispatches directly.</p>
```

### Tree / hierarchy diagram

`<ul class="tree">` holds nested `<li>` elements, each containing a `<span class="tree-node">`. Nest another `<ul>` inside an `<li>` for children. Connector lines are produced by CSS border techniques driven by the nesting; no extra markup is needed. Apply a `.ref-*` class directly to a `.tree-node` to color that node.

```html
<ul class="tree">
  <li><span class="tree-node ref-blue">retryWorker</span>
    <ul>
      <li><span class="tree-node ref-amber">queueStore</span></li>
      <li><span class="tree-node">dispatch()</span></li>
    </ul>
  </li>
</ul>
```

### Horizontal flow diagram

`<div class="flow">` contains alternating `<span class="flow-step">` and `<span class="flow-arrow">→</span>` elements. Apply a `.ref-*` class to any `.flow-step` to color that step.

```html
<div class="flow">
  <span class="flow-step ref-blue">enqueue</span>
  <span class="flow-arrow">→</span>
  <span class="flow-step ref-amber">queueStore</span>
  <span class="flow-arrow">→</span>
  <span class="flow-step">dispatch</span>
</div>
```

### Proportional bar

`<div class="bar">` contains `<div class="bar-segment ref-*" style="width: NN%">` segments. The author sets each segment's width inline so the segments sum to 100%.

```html
<div class="bar">
  <div class="bar-segment ref-blue" style="width: 60%">main (60%)</div>
  <div class="bar-segment ref-teal" style="width: 25%">feature (25%)</div>
  <div class="bar-segment ref-amber" style="width: 15%">hotfix (15%)</div>
</div>
```

### Timeline (bonus)

`.timeline` wraps `.timeline-row` items. Each `.timeline-row` pairs a `.timeline-label` with a `.timeline-track` containing an absolutely positioned `.timeline-bar`. Set the bar's position and width with the inline style `left:%; width:%`.

```html
<div class="timeline">
  <div class="timeline-row">
    <div class="timeline-label">branch cut</div>
    <div class="timeline-track"><div class="timeline-bar" style="left: 0%; width: 20%"></div></div>
  </div>
  <div class="timeline-row">
    <div class="timeline-label">review</div>
    <div class="timeline-track"><div class="timeline-bar" style="left: 20%; width: 45%"></div></div>
  </div>
</div>
```

### Block grid (bonus)

`.block-grid` holds `.block-grid-cell` units. Add `.is-filled` for a filled default cell, or add a `.ref-*` class to color a specific cell.

```html
<div class="block-grid">
  <div class="block-grid-cell is-filled"></div>
  <div class="block-grid-cell ref-green"></div>
  <div class="block-grid-cell"></div>
  <div class="block-grid-cell"></div>
</div>
```

### Comparison layout

`.compare` (two columns), `.compare-3`, or `.compare-4` wraps `.compare-col` blocks. Each `.compare-col` block starts with a `.compare-col-title`.

```html
<div class="compare">
  <div class="compare-col">
    <p class="compare-col-title">Before</p>
    <p>Polling every second regardless of queue state.</p>
  </div>
  <div class="compare-col">
    <p class="compare-col-title">After</p>
    <p>Event-driven dispatch triggered on enqueue.</p>
  </div>
</div>
```

### Tables

A plain `<table>` receives sensible default styling automatically. Add `.table-trace` for monospace, zebra-striped data or trace tables.

```html
<table class="table-trace">
  <thead><tr><th>ts</th><th>event</th><th>queue depth</th></tr></thead>
  <tbody>
    <tr><td>00:00.1</td><td>enqueue</td><td>1</td></tr>
    <tr><td>00:00.2</td><td>dispatch</td><td>0</td></tr>
  </tbody>
</table>
```

### Blockquote / cited comment

A plain `<blockquote>` accepts an optional trailing `<span class="cite">` (or any element with that class) for attribution. The label "Source:" before the citation is generated by CSS; do not type it yourself.

```html
<blockquote>
  <p>This still polls under the hood. Can we make it event-driven instead?</p>
  <span class="cite">@reviewer, PR #482</span>
</blockquote>
```

### Footer / source citations

`.doc-footer` wraps a closing note and an optional `.source-list` of links.

```html
<footer class="doc-footer">
  <p>Generated from commit <code>a1b2c3d</code> against <code>main</code>.</p>
  <ul class="source-list">
    <li><a href="#">PR #482</a></li>
    <li><a href="#">retryWorker.js</a></li>
  </ul>
</footer>
```

## Quick start skeleton

Copy this skeleton as the starting point for a new document, regardless of genre. Replace the kicker, the byline, the section headings, and the `id` attributes with whatever fits the document; the three-section shape (context, substance, consequences) fits a diff explanation, a system analysis, and a postmortem alike, but the headings themselves should not.

```html
<div class="doc">
  <header class="doc-header">
    <p class="kicker">DOCUMENT GENRE</p>
    <h1>Title of the document</h1>
    <p class="dek">One-sentence summary of the subject and the conclusion.</p>
    <p class="byline">Source identifier<span class="sep">·</span>date</p>
  </header>

  <nav class="toc">
    <p class="toc-title">Contents</p>
    <ol>
      <li><a href="#background">Section 1</a></li>
      <li><a href="#substance">Section 2</a></li>
      <li><a href="#consequences">Section 3</a></li>
    </ol>
  </nav>

  <section id="background">
    <h2>Section 1 heading</h2>
    <p>Context paragraph: what the reader needs to know before the rest of the document makes sense.</p>
  </section>

  <section id="substance">
    <h2>Section 2 heading</h2>
    <p>The main content, using <code>inlineTokens</code> and <code class="ref-blue">refColoredEntities</code> as needed.</p>
  </section>

  <section id="consequences">
    <h2>Section 3 heading</h2>
    <div class="admonition warning">
      <p>Anything the reader should watch for or act on.</p>
    </div>
  </section>

  <footer class="doc-footer">
    <p>Provenance line: where this document came from.</p>
  </footer>
</div>
```

Typical section headings by genre:

- Diff explanation: Background, What changed, Risks.
- Code review summary: Summary of the change, The fix, Open questions.
- System analysis: Background, How it works, Where it breaks down.
- Postmortem: Timeline, Root cause, Impact, Remediation.
