Overview

When an alert rule transitions to Alerting, five internal components decide in sequence whether a notification is sent. This document describes that path in full. The evaluation loop detects the state change. The per-organization Alertmanager owns routing for that tenant. The dispatch machinery performs matching, inhibition, silencing, and deduplication. Together these steps turn one state change into zero or more outbound notifications.

The component names below (MultiOrgAlertmanager, Dispatcher, Inhibitor, Silencer, NotificationLog, Scheduler) use the same color in every diagram and in the prose. This coloring allows a single component to be traced through the entire pipeline.

This document describes the alerting stack as implemented today in pkg/services/ngalert. That package vendors and extends the upstream Prometheus Alertmanager packages (dispatch, inhibit, silence, nflog) to support multiple tenants. If a reader is familiar with vanilla Alertmanager, the internals described here will be recognizable. The tenancy layer above those packages is specific to Grafana.

Component map

Each Grafana organization receives its own isolated Alertmanager instance. A single MultiOrgAlertmanager creates and supervises every instance. Inside each per-organization instance, four components cooperate to turn a batch of firing alerts into notifications:

  • MultiOrgAlertmanager
    • Dispatcher
    • Inhibitor
    • Silencer
    • NotificationLog

The Dispatcher owns the route tree and decides which receivers a group of alerts should reach. Before it sends a notification, it consults the Inhibitor to check whether a higher-severity alert already suppresses this alert. It also consults the Silencer to check whether the label set has been explicitly muted. After a notify attempt, the outcome (success, failure, or already sent) is recorded in the NotificationLog. This record is what makes retries and repeat intervals idempotent.

Per-org isolation

Each of the four components is instantiated once per organization and holds no cross-tenant state. The function newAlertmanager in alertmanager.go constructs a fresh Dispatcher, Inhibitor, Silencer, and NotificationLog for each organization. Each set is backed by that organization's own BoltDB-style key-value store file on disk. The MultiOrgAlertmanager performs only lifecycle management. It starts a new organization's Alertmanager on the first alert rule. It synchronizes configuration on change. It stops an organization's Alertmanager when the organization is deleted.

From evaluation to dispatch

At runtime, a single evaluation tick moves through five hops before a notification is sent externally:

Scheduler→ MultiOrgAlertmanager→ Dispatcher→ NotificationLog→ Integrations
Scheduler MultiOrgAlertmanager Dispatcher NotificationLog Integrations (uncolored; described below)

The Scheduler ticks at every base interval (10 seconds by default) and calls ruleEval.Evaluate against every rule due for evaluation. A rule that transitions to Alerting or Resolved is handed to MultiOrgAlertmanager.ProcessEvalResults. That function looks up the correct per-organization Alertmanager and forwards the alert. The Dispatcher then takes over. It groups the alert with any others that share the same group_by labels. It waits out group_wait. It matches the group against the route tree. A successful match writes an entry to the NotificationLog before Integrations sends anything over the wire. Integrations refers to the concrete receiver implementations for Slack, PagerDuty, email, and generic webhooks.

How an alert is routed

The Dispatcher matches alerts against a route tree in depth-first order. It stops at the first matching node unless that node sets continue: true. A payments-team alert with severity="critical" matches the top-level PagerDuty route and stops there. This prevents a critical payments outage from being silently double-routed to a low-priority Slack channel. A non-critical payments alert falls through to the team-scoped Slack route instead:

pkg/services/ngalert/notifier/alertmanager.go: default route tree
route:
  receiver: default-email
  group_by: ['alertname', 'grafana_folder']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - matchers:
        - severity="critical"
      receiver: pagerduty-oncall
      continue: false
    - matchers:
        - team="payments"
      receiver: payments-slack
      continue: true

That last continue: true is deliberate. The payments team requires a copy of every alert forwarded to a shared observability webhook further down the tree, regardless of severity. Routing does not stop after the Slack match for this reason.

Route matching operates on the labels attached to the alert instance, not on the alert rule definition. If a rule's query returns multiple series, then each series becomes its own alert with its own label set. Each such alert can be routed differently. This behavior is a common source of confusion: a rule may show a receiver configured in the UI, while individual alert instances still page the wrong team.

A slow webhook blocked the notification cycle

The Dispatcher notifies each receiver in a group synchronously before moving to the next group. Because of this, a single failing Integrations target could stall the entire batch. WebhookNotifier.Notify called SendWebhook with whatever context it was handed, usually the request-scoped context with no deadline of its own. A webhook endpoint that accepted the TCP connection and then never responded would hang the goroutine indefinitely.

Before the fix below was applied, one team's misconfigured internal webhook receiver, sitting behind a load balancer with no read timeout, caused a 20-minute backlog of unrelated Slack and email notifications during an incident. This delay occurred at the exact time prompt alert delivery mattered most.

pkg/services/ngalert/notifier/channels/webhook.go

HEAD

func (wn *WebhookNotifier) Notify(ctx context.Context, as ...*types.Alert) (bool, error) {
    resp, err := wn.ns.SendWebhook(ctx, wn.buildRequest(as))



    if err != nil {
        return true, fmt.Errorf("send webhook: %w", err)
    }
    defer resp.Body.Close()
    return resp.StatusCode/100 == 2, nil
}

NEW

func (wn *WebhookNotifier) Notify(ctx context.Context, as ...*types.Alert) (bool, error) {

    ctx, cancel := context.WithTimeout(ctx, wn.settings.Timeout)
    defer cancel()
    resp, err := wn.ns.SendWebhook(ctx, wn.buildRequest(as))
    if err != nil {
        return true, fmt.Errorf("send webhook: %w", err)
    }
    defer resp.Body.Close()
    return resp.StatusCode/100 == 2, nil
}

The retry flag now returns true correctly on timeout as well. As a result, an endpoint that is slow but eventually successful is retried on the next group_interval instead of being marked as permanently failed.

If wn.settings.Timeout is raised for an integration, check it against group_interval. A timeout longer than the group interval can let two notify attempts for the same group overlap. The NotificationLog deduplicates on group fingerprint plus receiver, not on in-flight request identity. Overlapping attempts can therefore result in duplicate pages to the same on-call engineer.

Single-tenant versus multi-org: a comparison

The multi-org rework replaced one process-wide Alertmanager with one instance per organization. The comparison below states what changed at the component level:

Before: a single shared Alertmanager

One Dispatcher, one Silencer, and one NotificationLog served every organization on the instance. All three read a single, unpartitioned route tree keyed by an org_id label matcher attached to every rule.

If the label matchers overlapped, a misconfigured route for one organization's rules could silently discard another organization's alerts. In addition, a single slow receiver anywhere stalled dispatch for all tenants.

After: the MultiOrgAlertmanager

Each organization receives its own Dispatcher, Inhibitor, Silencer, and NotificationLog, backed by an isolated on-disk store. Route trees are configured per organization through the UI. By construction, a route tree can no longer match another tenant's labels.

A slow or failing receiver in one organization's configuration no longer has a code path back into another organization's Dispatcher goroutine.
