Background

When a dashboard with several panels loads, six or eight panels often issue the identical datasource query within the same render tick. Each such request specifies the same time range, the same expression, and the same variables. Each request currently reaches the datasource independently. This behavior multiplies query load on Prometheus or Loki by a factor of N and provides no benefit.

PR #4821 introduces a coalescing layer in front of DatasourceQueryService.Query. This layer allows concurrent, identical requests to share a single upstream call. Two candidate implementations were built and load-tested before either was proposed as the mainline patch.

Both approaches use the same call site, pkg/services/query/handler.go. Both approaches are gated by the feature flag queryRequestDedup. Either approach can be swapped in without changes to call sites elsewhere in the codebase.

Approach A: mutex-guarded map

The first approach introduces a hand-rolled QueryCoalescer. The coalescer keeps an in-flight map keyed by a hash of the query fingerprint, guarded by a single sync.Mutex. Late arrivals block on a per-key sync.WaitGroup and read the result once the leader request completes.

type QueryCoalescer struct {
	mu       sync.Mutex
	inFlight map[string]*pendingQuery
}

type pendingQuery struct {
	wg     sync.WaitGroup
	result *QueryResult
	err    error
}

func (c *QueryCoalescer) Query(ctx context.Context, req *QueryRequest, fn func() (*QueryResult, error)) (*QueryResult, error) {
	key := req.Fingerprint()

	c.mu.Lock()
	if p, ok := c.inFlight[key]; ok {
		c.mu.Unlock()
		p.wg.Wait()
		return p.result, p.err
	}
	p := &pendingQuery{}
	p.wg.Add(1)
	c.inFlight[key] = p
	c.mu.Unlock()

	p.result, p.err = fn()
	p.wg.Done()
	return p.result, p.err
}

The flagged line never deletes key from c.inFlight after the leader request finishes. Every distinct fingerprint ever queried remains resident for the lifetime of the process.

A load test against a 40-panel dashboard ran for 6 hours. Over that period, QueryCoalescer.inFlight grew to 118,000 entries and retained approximately 340MB of *QueryResult pointers. Completed entries are never evicted. This is a memory leak, not a benchmarking artifact. The leak reproduces with go test -run TestCoalescer_Leak -race.

"This implementation leaks an entry per unique fingerprint indefinitely. The fix requires either a TTL sweep or a delete-on-completion path. The delete-on-completion path introduces its own race condition if a third request arrives between p.wg.Done() and the delete. This package should not reinvent singleflight."

Priyanka Rao, review comment on PR #4821

Approach B: singleflight.Group

The second approach replaces the hand-rolled map with golang.org/x/sync/singleflight. This approach also adds a small resultBroadcaster wrapper. The wrapper exists so that callers needing only a read-only snapshot, such as the panel viewer, do not retain a reference to the original mutable result.

pkg/services/query/dedup_singleflight.go
type QueryCoalescer struct {
	group      singleflight.Group
	broadcast  *resultBroadcaster
}

func (c *QueryCoalescer) Query(ctx context.Context, req *QueryRequest, fn func() (*QueryResult, error)) (*QueryResult, error) {
	key := req.Fingerprint()
	v, err, shared := c.group.Do(key, func() (interface{}, error) {
		res, err := fn()
		c.broadcast.publish(key, res)
		return res, err
	})
	metrics.CoalescedRequestsTotal.WithLabelValues(strconv.FormatBool(shared)).Inc()
	if err != nil {
		return nil, err
	}
	return v.(*QueryResult), nil
}

singleflight.Group deletes its internal call entry the moment fn returns. As a result, there is no map to sweep and no TTL to tune. The resultBroadcaster is new. It notifies subscribers of a completed coalesced query without handing them the same pointer the leader goroutine is still mutating during serialization.

singleflight.Group.Do shares one result object across every waiter. For this reason, resultBroadcaster.publish must deep-copy the result before handing it to subscribers. The leader goroutine in handler.go holds a mutable reference until it finishes writing the HTTP response.

Side-by-side comparison

Approach A: mutex map

  • This approach requires no new dependency. It adds approximately 40 lines of first-party code.
  • Testing confirmed a memory leak under sustained load. Entries are never evicted.
  • The wait path uses sync.WaitGroup. This mechanism cannot carry a context.Context cancellation into waiters.
  • The implementation is straightforward to step through in a debugger.

Approach B: singleflight

  • This approach adds golang.org/x/sync. This package is already an indirect dependency elsewhere in the module.
  • The map is self-cleaning. No growth was observed over the same 6-hour soak test.
  • Waiters observe the caller's ctx cancellation because fn closes over it directly.
  • This approach requires the extra resultBroadcaster copy step to avoid shared-mutation bugs.

For approach A, the inFlight entries column is the leading indicator, not RSS. RSS growth lags entry growth because Go's allocator does not immediately return freed pages to the operating system. A shorter soak test would have made this leak easy to miss.

Recommendation

Approach B should be shipped. The singleflight.Group primitive already solves the eviction problem that affected approach A. The primitive is a well-exercised dependency: it backs coalescing in groupcache and in several parts of the Go toolchain. The added resultBroadcaster copy step is a small, isolated cost. This cost is necessary for correctness under concurrent mutation.

If a future profile shows that the deep-copy in resultBroadcaster.publish is hot, then QueryResult should be made immutable after construction instead of removing the copy. This change closes the mutation hazard at the source instead of reintroducing it under load.
