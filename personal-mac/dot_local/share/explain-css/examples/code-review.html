Code Review Summary

Fix duplicate job execution in LeaseManager

A check-then-act race between the lease renewal path and the expiration sweep allowed two workers to hold the same job lease under load. A single webhook delivery job could then execute twice, sending two POST requests instead of one.

Summary

Between 2026-08-06 and 2026-08-09, the notifications team observed an increase in duplicate webhook deliveries. The same event id was posted to a customer endpoint twice, with a gap of roughly 40 to 90 milliseconds between deliveries. The duplicates occurred almost exclusively under high dequeue rates. Investigation traced the defect to LeaseManager, the component WorkerPool uses to ensure that only one worker owns a given job at a time. This PR closes the race condition that allowed two workers to hold the same lease simultaneously. It also adds a regression test that reproduces the interleaving deterministically.

Root cause

The lease lifecycle proceeds as follows. A worker dequeues a job and acquires a lease from LeaseManager. The worker then spawns a background goroutine that periodically renews the lease while the job runs, and releases the lease when the job finishes. A separate background loop, sweepExpiredLeases, walks the lease table and evicts any lease past its TTL. This eviction handles the case where a worker crashed without releasing its lease.

JobQueue.Dequeue → LeaseManager.Acquire → WorkerPool.runJob → sweepExpiredLeases
LeaseManager: owns the lease table WorkerPool: runs jobs and spawns renewal goroutines lease sweeper: background eviction loop

LeaseManager.Renew read lease.AcquiredAt and compared it against the TTL without holding the map's mutex. It then wrote back an updated timestamp. If sweepExpiredLeases ran its own TTL check and deleted that same lease during the gap between the read and the write, the renewal wrote a timestamp back to an entry that had already been removed. At the same time, a second worker's Acquire call found no entry for that job id and created a new lease for the same job. Two workers ended up holding two separate leases for the same job.

Before / after

Before: unsynchronized renew

LeaseManager.Renew checked AcquiredAt and updated it outside any lock. sweepExpiredLeases could delete the same entry during that check. A deleted lease id was indistinguishable from a lease id that had never been issued. As a result, a second WorkerPool acquire for the same job succeeded silently.

After: lock-guarded renew, soft eviction

LeaseManager.Renew now holds m.mu for its entire read-modify-write operation. sweepExpiredLeases marks a lease evicted instead of deleting it while a renew is in flight. The sweeper also skips any lease that is currently mid-renewal.

The fix

The fix requires two changes to internal/scheduler/lease_manager.go and one change to the worker pool. The worker pool change ensures that a released lease does not keep renewing after the job is done.

internal/scheduler/lease_manager.go

HEAD

func (m *LeaseManager) Renew(leaseID string) error {
    lease, ok := m.leases[leaseID]
    if !ok {
        return ErrLeaseNotFound
    }
    if time.Since(lease.AcquiredAt) > m.ttl {
        return ErrLeaseExpired
    }










    lease.AcquiredAt = time.Now()
    return nil
}

NEW

func (m *LeaseManager) Renew(leaseID string) error {







    m.mu.Lock()
    defer m.mu.Unlock()

    lease, ok := m.leases[leaseID]
    if !ok {
        return ErrLeaseNotFound
    }
    if lease.evicted {
        return ErrLeaseExpired
    }
    lease.AcquiredAt = time.Now()
    return nil
}

The sweeper is also changed so that it does not remove a lease that a renewal is actively updating:

internal/scheduler/lease_manager.go

HEAD

func (m *LeaseManager) sweepExpiredLeases() {
    m.mu.Lock()
    defer m.mu.Unlock()

    for id, lease := range m.leases {
        if time.Since(lease.AcquiredAt) > m.ttl {
            delete(m.leases, id)
        }




    }
}

NEW

func (m *LeaseManager) sweepExpiredLeases() {
    m.mu.Lock()
    defer m.mu.Unlock()

    for id, lease := range m.leases {



        if time.Since(lease.AcquiredAt) > m.ttl && !lease.renewing {
            lease.evicted = true
            delete(m.leases, id)
        }
    }
}

The call site that spawns the renewal goroutine was the other part of the fix. It had no way to stop renewing once Release was called. This gap let a renewal race a sweep long after the job itself had finished:

internal/scheduler/worker_pool.go
func (p *WorkerPool) runJob(job Job) {
    lease, err := p.leases.Acquire(job.ID, p.leaseTTL)
    if err != nil {
        return
    }
    go p.leases.KeepAlive(lease.ID, p.renewInterval)
    defer p.leases.Release(lease.ID)
    job.Execute()
}

The highlighted line requires the most attention in review. KeepAlive now takes a context.Context tied to the job's lifetime. It exits as soon as Release is called, instead of relying on the lease to expire on its own.

Risk and nitpicks

This fix closes the specific interleaving reproduced above. LeaseManager still trusts a bare leaseID string with no fencing token. If lease hand-off between workers is added later, for example work stealing during rebalance, the same class of check-then-act error can recur in a different form. This risk warrants a follow-up ticket before that work begins. It is not a blocker for this PR.

The renewal interval is computed as p.leaseTTL / 2 in both worker_pool.go and the new test file. Two copies of this calculation now exist. Promoting it to an exported constant on LeaseManager would prevent the two values from drifting apart.

After this change lands, lease-acquire duplicates should be graphed as a metric. The metric would count Acquire calls for a job id already tracked as delivered. A regression of this kind would then appear on a dashboard before customers notice duplicate webhooks.

Review thread

This is a check-then-act race that is invisible in a diff but obvious once the interleaving is written out. The eviction flag is the correct approach, and it is safer than making delete-during-renew atomic. Approval is granted once the fencing-token follow-up has a ticket number.
