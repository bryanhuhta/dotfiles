# Explain HTML — shared format rules

Shared by the `explain-diff` and `explain-analyze` skills. Not a skill itself; it has no `SKILL.md` and is never invoked directly. Every rule below applies to both documents, so a change here changes both.

## Build

- Build the document using the explain-css system. Read `~/.local/share/explain-css/DESIGN.md` in full before writing any HTML, and follow its component catalog and rules exactly. Inline the complete contents of `~/.local/share/explain-css/explain.css` into a `<style>` block in the document's `<head>` so the output stays a single self-contained file with no external stylesheet link and no JavaScript.
- Use the page shell from the DESIGN.md skeleton: `.doc` wrapping a `.doc-header` (kicker/h1/dek/byline), a `.toc`, one `<section>` per top-level heading below, and a `.doc-footer`. Don't use tabs for the top-level structure.
- Name the file `<YYYY>-<MM>-<DD>-<project>-<description>.html` and save it in `/tmp`, outside the code repo. `<project>` is the name of the repo the document concerns; `<description>` is a short kebab-case slug for the subject. For example: `/tmp/2026-01-12-retryqueue-event-driven-dispatch.html`.
- Do not publish the file as a Claude cloud Artifact unless explicitly asked to.

## Diagrams and color

- For diagrams, use explain-css's diagram primitives (`.tree`, `.flow`, `.bar`, `.timeline`, `.block-grid`, `.compare`) rather than inventing new diagram markup or using ASCII art. Pick a small number of diagram families and reuse them across the document; include example data in system/data-flow diagrams.
- Use diagrams and figures liberally. A diagram that shows the real mechanism beats a paragraph describing it.
- Use `.ref-*` classes to bind each entity discussed (a function, file, module, or branch) to one color across both prose and diagrams, per DESIGN.md's rules, and accompany any `.ref-*` diagram with a `.legend`.

## Callouts and code

- Use `.admonition` variants (note/tip/warning/important/danger) for callouts, definitions, and edge cases — never a custom highlighted box.
- For code, use `<pre class="code-block"><code>` with one `<span class="line">` per line (`line-add`/`line-remove`/`line-focus` as needed); never type `+`, `-`, or `→` manually, they're generated by CSS.

## Prose

- Write in the RFC-style prose DESIGN.md specifies: precise, declarative, impersonal. No rhetorical questions, no "let's", no asides to the reader.
- Cut any sentence that doesn't add information — include only what the reader needs, and say it once.
- Explain with concrete examples over toy data rather than abstract description.
- Every claim about the code must be grounded in code that was actually read. Cite `path/to/file.go:120` for anything specific, and mark inference as inference rather than presenting it as observed behavior.
