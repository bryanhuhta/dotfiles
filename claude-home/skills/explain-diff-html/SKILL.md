# Explain Diff

Please make me a rich, interactive explanation of the specified code change.

It should have these sections:

- Background: Explain the existing system relevant to this change. (You should broadly explore surrounding code for this.) We don't know how much the reader already knows, so include a deep background for beginners (note that it can be skipped if the reader is already familiar), and then a more narrow background directly relevant to the change.
- Intuition: Explain the core intuition for the code change. The focus here is to explain the essence, not the full details. Use concrete examples with toy data. Use figures and diagrams liberally.
- Code: Do a high-level walkthrough of the changes to the code. Group/order the changes in an understandable way.

Format:

- Build the document using the explain-css system. Read `~/.local/share/explain-css/DESIGN.md` in full before writing any HTML, and follow its component catalog and rules exactly. Inline the complete contents of `~/.local/share/explain-css/explain.css` into a `<style>` block in the document's `<head>` so the output stays a single self-contained file with no external stylesheet link and no JavaScript.
- Use the page shell from the DESIGN.md skeleton: `.doc` wrapping a `.doc-header` (kicker/h1/dek/byline), a `.toc`, one `<section>` per top-level heading below, and a `.doc-footer`. Don't use tabs for the top-level structure.
- For diagrams, use explain-css's diagram primitives (`.tree`, `.flow`, `.bar`, `.timeline`, `.block-grid`, `.compare`) rather than inventing new diagram markup or using ASCII art. Pick a small number of diagram families and reuse them across the document; include example data in system/data-flow diagrams.
- Use `.ref-*` classes to bind each entity discussed (a function, file, module, or branch) to one color across both prose and diagrams, per DESIGN.md's rules, and accompany any `.ref-*` diagram with a `.legend`.
- Use `.admonition` variants (note/tip/warning/important/danger) for callouts, definitions, and edge cases — never a custom highlighted box.
- For code, use `<pre class="code-block"><code>` with one `<span class="line">` per line (`line-add`/`line-remove`/`line-focus` as needed); never type `+`, `-`, or `→` manually, they're generated by CSS. Use `.diff-split` for side-by-side before/after comparisons.
- Name the file `<YYYY>-<MM>-<DD>-<project>-<description>.html` and save it in `/tmp`, outside the code repo. `<project>` is the name of the repo the diff is from; `<description>` is a short kebab-case slug for the change. For example: /tmp/2026-01-12-retryqueue-event-driven-dispatch.html
- Do not publish the file as a Claude cloud Artifact unless explicitly asked to.
- Write in the RFC-style prose DESIGN.md specifies: precise, declarative, impersonal. No rhetorical questions, no "let's", no asides to the reader. Cut any sentence that doesn't add information — include only what's needed to understand the change, and say it once.
